---
name: a2a-connector
description: Delegate tasks to authorized A2A agents, track results, and operate WorkBuddy desktop or cloud receiving adapters.
---

Use this skill for actual Agent coordination. Prompt cards alone do not create connections.

## Readiness and authentication

Use `workbuddy-a2a auth status` for pairing and live tunnel health. Credentials alone do not prove a working tunnel. In enterprise mode, obtain the identity-bound one-time ticket from `/console` → Agent 管理 → 接入 Agent → Connector and follow the supplied enterprise installation instructions with the exact expected Agent ID. Do not fall back to old pairing on `organization_ticket_required`; only legacy Redis-only deployments use the pending approval URL, Agent ID and confirmation code. Do not approve another identity or repeat enrollment for ordinary calls.

For a locally hosted receiving adapter, `workbuddy-a2a setup --relay <user-provided WSS /connect URL> --name <Agent name>` starts the built-in authenticated PC adapter and one managed tunnel without an external origin. GUI auth uses `workbuddy-a2a auth connect`: no stdin, reading `A2A_RELAY_URL` on first use. These legacy pairing entry points do not bypass an enterprise ticket requirement; use the console's enterprise installer when required. Do not start another runner for the same state while pairing is pending. A Relay-hosted WorkBuddy receiver instead uses its WorkBuddy invitation/account authorization flow and does not require a local Connector on the user's computer.

For receiving tasks, use `workbuddy-a2a platform login` and give its Relay setup-guide URL to the user. It leads to official WorkBuddy account authorization and then shows the remaining setup steps. `platform status` reports OAuth status. GUI connection status uses `workbuddy-a2a connection status` and does not report connected merely because pairing succeeded. `auth status` remains pairing/tunnel diagnostics only. The Relay must have server-side app credentials configured. Never ask for client secrets or tokens in chat or task text.

During first desktop receiving setup, explain both required user actions before any task: (1) authorize the same WorkBuddy account used on the execution PC; (2) on that PC open WorkBuddy's bottom-left 连接移动端 → 小程序 and enable 允许移动端连接此设备. Keep the desktop logged in and online. `doctor` is read-only and returns `nextActions`; desktop online status does not verify the remote-control switch, so `desktopRemoteControl=manual_check_required` requires user confirmation. Do not modify WorkBuddy's private settings or enable remote access automatically. After setup has been confirmed, do not repeat this prompt on every task; show it again only when an actual prerequisite is missing.

Cloud receiving uses its own guide and account authorization; it does not require a PC remote-control switch. Pairing, controller OAuth, receiving-side WorkBuddy OAuth and remote-control permission are separate steps. If a target reports `workbuddy_not_authorized` or `blockedReason=workbuddy_channel_not_configured`, show the receiving machine's concrete next step to the user. Do not ask the controller to reauthorize or create another Agent identity as a workaround. A setup rejection is not a task still working; do not automatically retry it.

Cloud failures expose `metadata.failureStage`, `blockedReason`, `businessPromptAttempted` and `providerState`. If businessPromptAttempted is true, never resend a prompt. An explicitly requested `workbuddy-a2a resume TARGET_AGENT_ID A2A_TASK_ID` can recover only the original newly created session whose business prompt has never been attempted; it keeps every original ID and checks the provider session name. Do not automatically invoke resume or release to bypass an unresolved task. Receiver-side authorization remains separate from controller access.

Check the Relay mode before using recovery extensions: current enterprise forwarding does not expose ResumeCloudTask or ReconcileCloudTask, even if a local/legacy adapter implements them. The resume/reconcile CLI commands described here apply only where that extension is actually exposed; another permission grant does not enable it. For enterprise hosted WorkBuddy, query the original task with GetTask, which schedules eligible read-only recovery internally.

For cloud receiving, first setup with `--mode cloud`; optionally bind `--task-id <actual-cloud-session-id>` and `--cwd /workspace`. Do not confuse a Buddy application ID with a cloud task ID. No binding means new sessions per new context. Cloud needs user.task.readable and user.task.invokable; cloud doctor checks readable tasks/bound-session status, not PC online status. The runtime needs Node.js 22 and persistent outbound connectivity. Cloud-hosted controllers can use the same CLI when installed and authorized in their execution environment. Configuration alone does not install or authorize tools. Separate identities require their own credentials and upstream authorization. Relay supports an explicit workbuddy.agentIds list as well as its legacy single WORKBUDDY_AGENT_ID; do not copy credentials between users.

Server-hosted receivers can use hybrid mode: one identity supports official cloud and PC APIs, without running this project's A2A server/Connector on the user's computer. Select message.metadata.workbuddyMode=cloud|desktop, or use call TARGET --mode cloud|desktop. Read the Agent Card's defaultExecutionMode. New requests default to cloud unless configured otherwise; followups and duplicate message IDs keep their original mode. Never reuse a context/message ID to switch execution location. Desktop execution still requires the official PC app online, the correct account authorization, and the user's remote-control setting. Cloud execution does not require the user's PC. Hosted credentials and journals remain on the receiving server; each configured identity has separate state.

## Delegation

1. Run `workbuddy-a2a targets`. Record callerAgentId and choose an exact authorized Agent ID suited to the task. In enterprise mode the administrator grants access on the **target's** row at `/console` → Agent 管理 → 谁能访问 (older UI: 授权) → 机器调用方 → this caller. The direction is caller → target; selecting the target on the caller's row grants the reverse direction. `/pair/list` applies only to legacy deployments. Do not substitute credentials or confuse an MCP Controller with a Connector identity.
2. Pass the user's authorized task text through stdin to `workbuddy-a2a call <target-agent-id> --message-id <unique-request-id>`. Reuse an ID only for the exact same target and task. The command constructs the required ROLE_USER message, text parts and messageId, saves a request journal before sending and returns JSON with task/context IDs, state, text and request identifiers. A connection check does not itself authorize a real test task. Prefer this client to hand-written curl.
3. Query an active task with `workbuddy-a2a task <target-agent-id> <task-id>`.
4. After timeout, disconnect or uncertain dispatch, use `workbuddy-a2a outbound <relay-request-id>`. This recovers the original response or polls an existing task, without sending another task. Missing or expired Relay logs do not prove non-execution. Never assign a new message ID merely to retry an uncertain task. Only an explicit local `dispatched:false` preflight failure permits retry with the same ID after correcting its cause.
5. Report actual results; distinguish submitted, working, awaiting input, completed, failed, canceled, rejected and unknown states. Failed/canceled/rejected return nonzero. Input-required is not successful completion.

After a completed round, use `--context-id <returned-context-id>` for a follow-up in the same target context. Use a new message ID for a new instruction, retaining it for exact retries. Results include available artifact text/locations and metadata.

## Enterprise permissions and diagnostics

The card needs discover; sending needs invoke; reading a task needs task_read **and ownership by this caller identity**. Personal callers also need their bound member's effective direct/group permissions intersected with explicit machine grants; service callers use machine grants. The token needs call scope and the Agent must be active/canCall; administrator status does not bypass these rules. Connection, enrollment, account OAuth, member access and machine grants are separate checks.

Enterprise Relay does not expose unfiltered `ListTasks` / `tasks/list` (501 rpc_method_not_supported; older versions returned 403). This does not imply missing invoke permission. Query your saved task IDs; a random task or old caller's task can return 403 despite a correct invoke grant. JSON-RPC -32602 indicates parameter validation, not an ACL failure. A readable card establishes discovery only.

Durable Relay receipts work in enterprise mode. JSON-RPC id, stable messageId, relayRequestId and A2A taskId are distinct. A receipt 404 can mean wrong caller, no/expired reservation, or revoked access; do not infer that enterprise mode has no journal or that nothing executed. Raw HTTP without messageId/Idempotency-Key may create no receipt; X-Relay-Request-Id alone is insufficient. Exact retries keep all input and keys; changed input under an existing key returns 409. Preserve original IDs and recover after uncertainty rather than creating another task, including after cloud timeouts.

## Receiving tasks

The PC adapter accepts text `SendMessage` requests and implements local `GetTask` / `ListTasks`. Enterprise Relay permits owned GetTask but blocks the unfiltered ListTasks collection even if the adapter supports it. Local diagnostics: `workbuddy-a2a adapter task <task-id>`. The Relay checks controller grants, and the adapter separately authenticates loopback requests.

Each task includes `[A2A_TASK:<id>]`. Execute the authorized task normally and preserve that ID. The final reply must be one JSON object with `a2aTaskId`, `status` (`completed`, `failed`, `input-required`) and `text` containing results, output locations, verification evidence or a blocking question. Do not emit completed during planning. This is required because the PC history API has no independent completion event.

The PC assistant is a shared conversation, not an isolated cloud sandbox. Only one unresolved incoming task is permitted. Do not submit another while the current task runs, needs input, or has an unknown outcome. Durable records survive restarts and reconcile existing messages without resending.

PC approvals and AskQuestion interactions stay in the desktop; never auto-approve them. PC provider cancellation is unsupported, so stopping the tunnel does not cancel execution. No attachment upload is claimed.

## Cloud receiving

Cloud uses Open API plus ACP initialize/load/prompt. Do not impose the desktop final-JSON convention on cloud tasks: the matching prompt response or session/endTurn correlated to the live echoed user prompt and provider request ID is authoritative. end_turn completes, refusal rejects, cancelled cancels, other stop reasons require inspection. History replay from session/load is not this round's live result. Where a local/legacy deployment exposes the extension, an explicitly requested `workbuddy-a2a reconcile TARGET_AGENT_ID A2A_TASK_ID` checks the original owned session, uniquely matches the exact user prompt and its provider turn, then requires a unique matching endTurn. It never submits a prompt and refuses ambiguous history or missing completion signals. Enterprise hosted receivers instead schedule that read-only recovery from GetTask. A new cloud session starts with an initialization-only READY turn, then submits the real instruction exactly once through ACP.

Use `workbuddy-a2a cloud tasks` or `cloud task <cloud-task-id>` for safe provider status, and `adapter task <A2A-task-id>` for the local journal. Binding always uses the specified existing session and never silently creates a replacement. Bound contexts share one cloud session. Serialized incoming turns reject overlap and unresolved outcomes.

When task metadata contains permission, show the user its tool details and options. Only after an explicit user choice use `workbuddy-a2a permission <target-agent-id> <A2A-task-id> <request-id-as-JSON> <option-id>`. Preserve string versus numeric request ID and the exact supplied option ID; never select an approval just to continue. Example string argument: `'"permission-1"'`. For a requested cancellation, use `workbuddy-a2a cancel <target-agent-id> <A2A-task-id>`, then query until the actual canceled stop reason arrives. A cancel send is not proof of remote termination.

Cloud disconnects, uncertain creation/sends or runner restarts retain original IDs without resubmission. Surface the unresolved state and ask the user to inspect the original WorkBuddy session; do not infer current-round completion from old history or overall session status. Creation uncertainty retains cloudName=A2A-<task-id> for provider lookup. Streamed artifact URIs are provider locations, not guaranteed public download URLs. ACP credentials remain in process memory and never belong in output or journals.

The receiver automatically performs read-only reconciliation of eligible prompted tasks in their original owned sessions after restart or disconnect, retrying every 30 seconds. Ordinary GetTask also schedules recovery; no self-call ACL is required. When metadata.recoveryState is pending or awaiting_evidence, continue querying the original task ID: these are unresolved recovery states, not a request to resend or release. Only unique matching user/provider/endTurn evidence and recovered result text produce a verified terminal result. Missing result text never falls back to an old partial live answer. Explicit reconcile is limited to deployments that expose that extension, as described above. Automatic recovery cannot run while the receiver host is suspended or offline.

GetTask can expose recovered content before completion is verified. With recoveryState=output_recovered and completionVerified=false, relay the recovered text as unverified output, not successful completion. recoveryBlockedReason and recoveryEndTurnCount distinguish missing or conflicting end signals. The receiver also restores original-session artifacts through the official sandbox REST API; artifacts may be readable while state remains input-required. They belong to the original cloud session and do not by themselves prove the business turn completed. Do not discard readable text/artifacts just because explicit reconcile reports missing endTurn. Identical repeated endTurn notifications are idempotent; conflicting stop reasons remain unresolved.

Only after the user explicitly asks to abandon unresolved tracking, use `workbuddy-a2a release <target-agent-id> <A2A-task-id> [recovered-cloud-task-id]`. It requires no live ACP turn and an inactive provider session; recovered creation IDs must match cloudName. It closes local tracking as rejected, never as completed or remotely canceled. Do not automatically release unknown tasks to make the queue accept new work.

## Operations

Use `stop` / `start` for the managed service. Run `platform logout` to remove encrypted server-side WorkBuddy tokens before `auth logout` removes local pairing credentials. Status commands are read-only. Diagnose offline/pending state before repairing or pairing again.

State is outside the package in `~/.config/a2a-connector/`. `A2A_CONNECTOR_INSTANCE` isolates instances; `A2A_CONNECTOR_CONFIG_DIR` chooses a private directory. Never print/upload credentials, pending request IDs, pairing codes, local Bearer tokens or OAuth/ACP tokens. Preserve journals on uncertain execution and report task/request IDs instead of private file contents.
